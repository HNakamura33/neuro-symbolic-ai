## 共通実験設計

### 比較条件

| 条件 | 構成 | 目的 |
|---|---|---|
| **B0** | LLM 単体(ツールなし)。事実は与えない | パラメトリック知識の限界の確認 |
| **B1** | LLM + 全事実をプロンプトに同梱(long-context ベースライン) | 「文脈に入れれば済む」への反論。最も強いベースライン |
| **C1** | nsai(記号ツールあり・サブエージェントなし) | 記号層そのものの寄与 |
| **C2** | nsai フル(サブエージェント委譲あり) | 委譲の追加寄与(アブレーション: C2−C1) |

- B1 は KB の全トリプルを Turtle のままプロンプトに入れる。KB 規模スケーリング(実験2)では
  B1 の劣化曲線こそが本論文の核になるので必ず含める。
- C1/C2 の差分はコード上 `build_options` の `agents=` / `Task` の有無のみ
  (実験ハーネスにフラグを追加する)。

### モデルと反復

- メインモデル: sonnet を主系、opus と haiku で各実験の代表設定のみ追試
  (モデル汎化の確認。全格子は回さない)。
- サブエージェント: 実装既定(explorer/auditor = haiku、他 = 継承)。
  RQ5 では explorer/auditor を sonnet に変えた条件を追加。
- 反復: 合成データは各設定 **5 run**、公開ベンチマークは規模が大きいので
  **3 run**(LLM の確率性対策)。平均±標準偏差を報告。
- 統計検定: 同一問題セットに対する対応ありの比較なので
  McNemar 検定(2値正誤)/ paired bootstrap(連続値)。有意水準 5%。

### 共通の測定項目

全実行で記録する(ハーネスが JSONL に落とす):

- 正誤・判定ラベル(タスク固有)
- コスト(`ResultMessage.total_cost_usd`)、入出力トークン数
- ツールコール数(種類別)、ターン数、壁時計時間
- プロンプト・モデル・シードのバージョンスタンプ(再現性)

### データセット方針

**合成データと公開ベンチマークのハイブリッド。** 役割を分ける:

- **合成 KB(制御実験)** — 難易度(ホップ数、規模、矛盾数)を独立に制御でき、
  正解が構成的に自明で、汚染ゼロ。スケーリング曲線・損益分岐など
  「何が効いているか」の分析はこちらで行う
- **公開ベンチマーク(外的妥当性・比較可能性)** — 先行研究と数字を突き合わせ
  られる土俵。KB やトリプル・ルールが**明示的に付属する**ものを優先して選ぶ
  (テキストのみのベンチマークは検索・抽出の性能が交絡するため)

| ベンチマーク | 使う実験 | 適合理由 |
|---|---|---|
| **MetaQA**(WikiMovies KB、1/2/3-hop QA) | 実験2 | KB がトリプルで付属 — そのまま RDF ロード可。マルチホップ QA の標準セット |
| **CLUTRR**(家系推論、合成・構成的汎化) | 実験2 | 関係合成の系統的難易度制御。k-hop 汎化の報告様式が確立している |
| **2WikiMultiHopQA**(トリプル形式の根拠付き) | 実験2(サブセット) | 根拠がトリプルで付属し、`ingest` 経由の「テキスト→KB→推論」全パイプライン評価に使える |
| **ProofWriter / ProntoQA**(ルールベース演繹、closed-world) | 実験1 | 事実+ルールから entailed / contradicted / unknown を判定 — nsai の3値判定と完全に同型 |
| **FEVER**(事実検証、3値ラベル) | 実験1(サブセット) | SUPPORTED/REFUTED/NEI ≒ entailed/contradicted/unknown。根拠文を ingest してから検証させ、抽出層込みの評価とする |
| **HumanEval+ / MBPP+**(EvalPlus) | 実験4a/4b | 拡張テストが境界ケースを重点評価。テスト生成の mutation 比較の土台 |
| **QuixBugs** | 実験4a | 単一欠陥(多くが境界・オフバイワン)の修正ベンチマーク |
| **SWE-bench Verified**(境界バグサブセット) | 実験4d(副次) | 実リポジトリの実バグで外的妥当性を担保。修正パッチが境界・演算子・±1 変更のタスクのみ抽出 |
| **LiveCodeBench**(カットオフ後問題) | 実験4a/4b の補強 | 構成上汚染フリーのコード問題源。自作スイートの補完に使う |

### スコープ外のベンチマークと理由

査読対応のため、使わない判断も計画に明記しておく:

- **フル SWE-bench / SWE-bench Lite 全体**: タスクの律速がリポジトリ探索・
  修正箇所特定・API 理解であり、本論文の主張(記号検証が境界・制約ロジックの
  正しさを上げる)の測定対象ではない。記号層の寄与が総合スコアで希釈され、
  高コスト(500 問 × 条件 × run、1 タスク数分〜数十分)で null result を
  買うことになる。→ 境界バグにフィルタしたサブセットのみ使う(実験4d)
- **Terminal-Bench 等の端末操作・運用系**: 測定対象(シェル操作、環境構築、
  運用タスク)がニューロシンボリック推論の主張と直交する。nsai の bash は
  設計上ユーザー確認ゲート付きであり、ハーネス前提も合わない
- **総合エージェント能力ベンチマーク全般**: 本論文は汎用コーディング
  エージェントとしての優位を主張しない。論文の Scope 節にこの線引きを書き、
  「どこで効いて、どこでは効かないか」を明示する方が主張として誠実で強い

### 汚染対策(公開ベンチマーク使用時)

学習データ汚染で B0 が不当に強くなり記号層の寄与が過小評価されるのが最大の懸念。
3つの対策を全公開ベンチマークに適用する:

1. **B0 を汚染プローブとして常時報告** — 事実を一切与えない B0 の正答率が
   高い項目は記憶で解けている。B0 正解項目を除いた **uncontaminated サブセット**
   での比較を主表に、全項目版を付録に置く
2. **条件間比較は同一文脈** — B1/C1/C2 は同じ事実集合を見るので、汚染は全条件に
   同方向に働き、**条件間の差分**は依然有効。絶対値でなく差分を主張の根拠にする
3. **摂動版の併用** — MetaQA / CLUTRR はエンティティ名を無作為な固有名に置換した
   摂動版を作成(KB ごと置換するので正解は保存される)。原版と摂動版のギャップ
   自体を「LLM 記憶依存度」の測定として報告する — 記号層は置換に不変のはず
   なので、C1/C2 のギャップ ≈ 0 が予測になる

## 実験1: 主張検証とハルシネーション抑制 (RQ1)

**タスク**: KB に対する主張の3値判定(entailed / contradicted / unknown)。

**データ**:

1. **合成**(主系): 合成 KB 生成器(後述)で家系・組織・地理ドメインの KB を生成
   (500 トリプル、owl:FunctionalProperty・rdfs:subClassOf・owl:sameAs/differentFrom を含む)。
   主張を各ラベル 100 問ずつサンプル:
   - *entailed*: 明示トリプル 50 + **推論でのみ導ける** 50(subClassOf 連鎖、functional+sameAs)
   - *contradicted*: functional 衝突 50 + differentFrom 衝突 50
   - *unknown*: KB が沈黙している尤もらしい主張 100(エンティティは実在、関係が未記録)
2. **ProofWriter / ProntoQA**(公開): 事実+ルールを KB にロードし
   (単純な含意ルールは rdfs:subClassOf / SPARQL に写像、写像不能な項目は除外して
   除外率を報告)、entailed / contradicted / unknown の3値判定。depth 別に報告
3. **FEVER dev サブセット 300 件**(公開): 根拠文を `ingest` で KB 化してから
   検証させる。抽出(定式化)層込みのエンドツーエンド評価で、
   SUPPORTED/REFUTED/NEI をそのまま3値ラベルに対応させる

**手順**: 各条件で `nsai verify` 相当のプロンプトを実行し、判定ラベルを構造化抽出。

**指標**:

- macro-F1(3値)
- **偽検証率**(本論文で最重要): 正解が contradicted / unknown の主張を
  「正しい/検証済み」と断定した割合。ハルシネーションの操作的定義
- unknown の正答率を独立に報告(LLM は unknown を苦手とし当て推量する、が仮説)

**期待される結果**: B0/B1 は推論必須問題と unknown で崩れ、C1 はほぼ天井
(kb_verify は決定論的なので、誤りは LLM の定式化ミスのみに局在する)。
**エラー分析で「残った誤りはすべて定式化層」であることを示す** — これが
ニューロシンボリック分業の直接の証拠になる。

## 実験2: マルチホップ QA と委譲の損益分岐 (RQ2)

**タスク**: 中間エンティティを要する質問への回答(「アリスの上司の出身地は?」)。

**データ**:

1. **合成**(スケーリング分析): KB を規模 {100, 500, 2000, 5000} トリプルで生成。
   各規模でホップ数 k ∈ {2, 3, 4, 6} の質問を 50 問ずつ、正解は構成時に確定。
   距離のばらつきを持つ「経路が事前に自明でない」質問
   (述語の選択にホップごとの判断が要るもの)を半数含める
2. **MetaQA**(公開・主戦場): 付属 KB(約13万トリプル)を RDF ロードし、
   1/2/3-hop 各 200 問サンプル。既存手法(KB-QA 系・LLM 系)と数字を直接比較できる。
   本実験最大の KB でもあり、委譲の損益分岐の実地検証を兼ねる。
   B1(全トリプル同梱)は 13万トリプルでは文脈に入らないため、
   「質問エンティティの 2-hop 近傍だけを同梱する B1′(オラクル検索付き
   long-context)」に置き換える — これは実務の RAG 構成にも対応する強い比較対象
3. **CLUTRR**(公開): 物語文を `ingest` で KB 化 → k-hop 家系質問。
   構成的汎化(訓練より長いホップ)の標準的な報告様式に乗せる
4. **2WikiMultiHopQA サブセット 300 問**(公開): 根拠トリプル付き。
   テキスト → KB → 推論のフルパイプライン評価
5. 公開3種すべてにエンティティ置換の**摂動版**を用意(汚染対策 §3)

**手順**: B1 / C1 / C2 で回答、Exact Match で採点。
C2 は explorer への委譲が実際に起きたかをツールログから確認し、
委譲率も報告する(メインが委譲基準に従うかどうか自体が結果)。

**指標と分析**:

1. EM をホップ数 × KB 規模のマトリクスで報告
2. **B1 の劣化曲線 vs C1/C2 の平坦さ**(KB 規模を x 軸に)
3. **委譲の損益分岐**: C1 と C2 のコスト・レイテンシ・EM を KB 規模別に比較。
   `docs/future-extensions.md` の「数百〜数千トリプルで真価」という予言を検証
4. explorer の報告した根拠パスの**全トリプル検証可能率**
   (返ってきたパスを機械的に kb_verify に通す — 100% が設計目標)

## 実験3: 矛盾検出の精度 (RQ3)

**タスク**: KB 全体から注入された矛盾を漏れなく・誤検出なく発見し、
食い違う出典まで特定する。

**データ**: クリーンな合成 KB(500 / 2000 トリプル)に矛盾を c ∈ {5, 20} 件注入:

- functional プロパティ衝突(同一主語に異なる値、出典を変えて記録)
- sameAs / differentFrom 衝突
- 推論を経てのみ衝突するもの(subClassOf 経由)を半数含める — LLM の目視走査が
  最も苦手とするはずのケース

provenance ログには注入時に相異なる `source` を記録しておく。

**条件**: B1(全トリプル+全出典ログを文脈で読ませて列挙させる)/
C1(メインがツールで走査)/ C2(kb-auditor へ委譲)。

**指標**: 矛盾検出の Precision / Recall / F1、出典ペア特定率、コスト。
KB 規模を上げたときの Recall の落ち方(B1 は文脈長で崩れる、が仮説)。

## 実験4: ハイブリッドコーディング (RQ4)

4つのサブ実験。4a–4c は `nsai code --full-auto`(bash 確認なし・ネットワーク
遮断のまま)、4d は依存インストール等でネットワークが要るため
`nsai code --bypass-permissions`(全許可)を使い捨てコンテナ内で使う。
いずれも実装済み。

### 4a. 境界バグの監査・修正

**データ**: (1) **QuixBugs**(Python 40 問、単一欠陥の多くが境界・オフバイワン)を
そのまま使用、(2) 自作の境界バグスイート 30 問(ページネーション、区間演算、
インデックス計算、日付、丸め — 隠しテストを別途保持)。自作分の半数は
**LiveCodeBench のカットオフ後問題**の正解実装にバグを植えて作り、
汚染フリー性を担保する。QuixBugs は汚染が既知なので、条件間差分と
自作スイートの結果を主、絶対値を従として報告する。

**条件**: 素のコーディングエージェント(ファイルツールのみ、= C1 から記号ツールを
除いた構成)vs `nsai code`(SMT あり)。

**指標**: バグ検出率、修正後の隠しテスト通過率、
smt_verify の反例がそのまま回帰テスト化された率(ツールログから)。

### 4b. テスト生成の変異検出力

**データ**: **HumanEval+ / MBPP+**(EvalPlus)の正解実装から、数値・境界ロジック
中心の 40 関数をサンプル + 自作 10 関数(制約が明示的なもの)。

**条件**: LLM 直書きテスト vs test-generator(反例・境界値・同値クラスの3系統)。
EvalPlus の拡張テスト自体を「専門家が境界を重点強化した参照点」として併記する。

**指標**: mutation testing(mutmut)による **mutation score**。
境界変異(`<` ↔ `<=`、±1)に限定したスコアを別掲 — ここで差が付くはず。
テスト数を揃えた比較(上位 n 件)も併記し「数で稼いだ」への反論とする。

### 4c. loop-judge と完了判定

**データ**: 「全テスト成功+宣言済み主張の証明」が完了条件の修正タスク 15 問。
うち5問は**わざと完了不能**(仕様が矛盾)にして発散検出を試す。

**条件**: LLM 自身の「もう大丈夫そう」判定 vs loop-judge 委譲。

**指標**: 早期完了率(完了宣言時に隠しテストが失敗している率)、
完了不能タスクでの STALLED 検出率(vs 無限ループ/諦め)、平均イテレーション数。

### 4d. SWE-bench Verified 境界バグサブセット(副次)

**目的**: 「実リポジトリの実バグでも効くのか」という査読者の当然の問いに、
主張の守備範囲内で答える。総合 SWE 能力の主張はしない(スコープ外 §参照)。

**データ**: SWE-bench Verified から、gold パッチが**境界・数値条件の小変更**
であるタスクを機械フィルタで抽出(比較演算子の変更 `<`↔`<=`、±1 定数、
min/max・clamp・範囲チェックの修正、日付/インデックス演算 — パッチの AST 差分で
判定)。目標 30–50 問。フィルタ条件とヒット数は必ず報告する。

**条件**: `nsai code`(記号ツールあり)vs 同一構成から記号ツールのみ除いた
アブレーション。**条件間差分のみ**を主張に使い、絶対スコアは参考値
(nsai はリポジトリ規模の運用に最適化されていないため)。

**指標**: 解決率(SWE-bench 公式ハーネス)、smt_verify が修正箇所の特定・
検証に実際に使われた率(ツールログ)、コスト。
3 run は高コストなので 1 run + 失敗タスクのみ再試行の 2 run 構成。

**リスク**: フィルタ後も探索が律速で差が出ない可能性。その場合も
「記号層の寄与は修正箇所特定後の検証段に限定される」という知見として
エラー分析に載せる(negative result を隠さない)。

## 副次実験 (RQ5, RQ6)

- **RQ5 コスト分析**: 実験2・3の C2 で、explorer/auditor を haiku → sonnet に
  変えた条件を追加。精度が同等でコストが数分の一、を示せれば
  「決定論的な地面の上では安いモデルで十分」という主張になる。
- **RQ6 code2kb**: OSS リポジトリ 3〜5 件(例: click, httpx 規模)に対し、
  (a) code2kb の import/呼び出しエッジと LLM 抽出(`ingest` にソースを渡す)の
  エッジ再現率を突き合わせ(ast 出力を正解系とする; LLM 抽出の網羅率が下がる
  ことを示す)、(b) 「関数 X を変更すると壊れうる呼び出し元は?」型の影響分析
  20 問を、構造層あり/なしで explorer に解かせ正答率を比較。

## リスクと対策

- **OWL-RL 閉包の計算コスト**: `kb_verify` は毎回全閉包を計算する実装
  (`kb.py:closure`)なので 5000 トリプルで遅くなり、MetaQA の 13万トリプルでは
  実行不能な恐れ。→ 週1で実測し、閉包キャッシュ(グラフ変更時のみ再計算)を
  先に入れる。MetaQA は OWL スキーマを持たないので、推論なしの直照合に
  フォールバックする経路も用意(実験結果には「システム改善」として書ける)
- **ベンチマーク変換の妥当性**: ProofWriter のルール写像やトリプル変換に
  恣意性が入ると批判される。→ 変換スクリプトを公開し、写像不能で除外した
  項目数・理由を必ず報告。FEVER は根拠文の抽出込み評価であることを明記
- **委譲不履行**: メインが委譲基準に従わず C2 ≒ C1 になる。→ 委譲率を必ず計測し、
  低ければ「委譲を強制した C2′」を追加条件にして上限性能と分離する
- **プロンプト感度**: ベースラインのプロンプトが弱いと批判される。→ B1 にも
  「段階的に推論せよ」「不明なら不明と言え」を入れた強化版を用意し、両方報告
- **採点の曖昧さ**: 自由回答の EM は表記揺れで壊れる。→ 回答を CURIE で
  返させる形式に固定(構造化出力)
- **学習データ汚染**: 公開ベンチマークでは B0 プローブ・条件間差分・
  エンティティ置換摂動版の3対策(§汚染対策)を必ず適用し、
  uncontaminated サブセットを主表にする

## 論文構成案

1. Introduction — LLM の確率的推論と検証可能性の欠如、分業アーキテクチャの提案
2. System — KB/OWL-RL/CSP/SMT ツール層、サブエージェント委譲、code2kb(既存実装の記述)
3. Experiments — RQ1–4(主)、RQ5–6(分析)
4. Error Analysis — 誤りの層別(定式化 / 委譲 / ソルバー)。「誤りが定式化層に
   局在する」ことを quantify できれば本論文の一番強い知見になる
5. Related Work — GraphRAG、tool-augmented LLM、LLM+SMT(例: 形式検証支援)、
   self-verification 系
6. Limitations — 単一 LLM ファミリー、閉世界の KB、ベンチマーク変換の写像損失
   (除外率を報告)、公開ベンチマークの汚染(対策込みでも完全排除は不能)

投稿先候補: NeSy、AAAI/IJCAI(ニューロシンボリック枠)、または
ACL/EMNLP Findings(tool-augmented LLM 枠)。実験規模的には後者が現実的。
