## 共通実験設計

### 比較条件

| 条件 | 構成 | 目的 |
|---|---|---|
| **B0** | LLM 単体(ツールなし)。事実は与えない | パラメトリック知識の限界の確認 |
| **B1** | LLM + 全事実をプロンプトに同梱(long-context ベースライン) | 「文脈に入れれば済む」への反論。最も強いベースライン |
| **C1** | nsai(記号ツールあり・サブエージェントなし) | 記号層そのものの寄与 |
| **C2** | nsai フル(サブエージェント委譲あり) | 委譲の追加寄与(アブレーション: C2−C1) |

- B1 は KB の全トリプルを Turtle のままプロンプトに入れる。KB 規模スケーリング(実験2)では
  B1 の劣化曲線こそが本論文の核になるので必ず含める。
- C1/C2 の差分はコード上 `build_options` の `agents=` / `Task` の有無のみ
  (実験ハーネスにフラグを追加する)。

### モデルと反復

- メインモデル: sonnet を主系、opus と haiku で各実験の代表設定のみ追試
  (モデル汎化の確認。全格子は回さない)。
- サブエージェント: 実装既定(explorer/auditor = haiku、他 = 継承)。
  RQ5 では explorer/auditor を sonnet に変えた条件を追加。
- 反復: 各設定 **5 run**(LLM の確率性対策)。平均±標準偏差を報告。
- 統計検定: 同一問題セットに対する対応ありの比較なので
  McNemar 検定(2値正誤)/ paired bootstrap(連続値)。有意水準 5%。

### 共通の測定項目

全実行で記録する(ハーネスが JSONL に落とす):

- 正誤・判定ラベル(タスク固有)
- コスト(`ResultMessage.total_cost_usd`)、入出力トークン数
- ツールコール数(種類別)、ターン数、壁時計時間
- プロンプト・モデル・シードのバージョンスタンプ(再現性)

### データセット方針

**すべて合成データを主とする。** 公開ベンチマーク(HotpotQA 等)は学習データ汚染で
B0 が不当に強くなり、記号層の寄与を過小評価するため。合成 KB は
汚染ゼロ・難易度(ホップ数、規模、矛盾数)を独立に制御可能・正解が構成的に自明、
という3点で本論文の主張検証に最適。外的妥当性は実験4(実コード)と RQ6(実 OSS
リポジトリ)で補う。

## 実験1: 主張検証とハルシネーション抑制 (RQ1)

**タスク**: KB に対する主張の3値判定(entailed / contradicted / unknown)。

**データ**: 合成 KB 生成器(後述)で家系・組織・地理ドメインの KB を生成
(500 トリプル、owl:FunctionalProperty・rdfs:subClassOf・owl:sameAs/differentFrom を含む)。
主張を各ラベル 100 問ずつサンプル:

- *entailed*: 明示トリプル 50 + **推論でのみ導ける** 50(subClassOf 連鎖、functional+sameAs)
- *contradicted*: functional 衝突 50 + differentFrom 衝突 50
- *unknown*: KB が沈黙している尤もらしい主張 100(エンティティは実在、関係が未記録)

**手順**: 各条件で `nsai verify` 相当のプロンプトを実行し、判定ラベルを構造化抽出。

**指標**:

- macro-F1(3値)
- **偽検証率**(本論文で最重要): 正解が contradicted / unknown の主張を
  「正しい/検証済み」と断定した割合。ハルシネーションの操作的定義
- unknown の正答率を独立に報告(LLM は unknown を苦手とし当て推量する、が仮説)

**期待される結果**: B0/B1 は推論必須問題と unknown で崩れ、C1 はほぼ天井
(kb_verify は決定論的なので、誤りは LLM の定式化ミスのみに局在する)。
**エラー分析で「残った誤りはすべて定式化層」であることを示す** — これが
ニューロシンボリック分業の直接の証拠になる。

## 実験2: マルチホップ QA と委譲の損益分岐 (RQ2)

**タスク**: 中間エンティティを要する質問への回答(「アリスの上司の出身地は?」)。

**データ**: 合成 KB を規模 {100, 500, 2000, 5000} トリプルで生成。
各規模でホップ数 k ∈ {2, 3, 4, 6} の質問を 50 問ずつ、正解は構成時に確定。
距離のばらつきを持つ「経路が事前に自明でない」質問
(述語の選択にホップごとの判断が要るもの)を半数含める。

**手順**: B1 / C1 / C2 で回答、Exact Match で採点。
C2 は explorer への委譲が実際に起きたかをツールログから確認し、
委譲率も報告する(メインが委譲基準に従うかどうか自体が結果)。

**指標と分析**:

1. EM をホップ数 × KB 規模のマトリクスで報告
2. **B1 の劣化曲線 vs C1/C2 の平坦さ**(KB 規模を x 軸に)
3. **委譲の損益分岐**: C1 と C2 のコスト・レイテンシ・EM を KB 規模別に比較。
   `docs/future-extensions.md` の「数百〜数千トリプルで真価」という予言を検証
4. explorer の報告した根拠パスの**全トリプル検証可能率**
   (返ってきたパスを機械的に kb_verify に通す — 100% が設計目標)

## 実験3: 矛盾検出の精度 (RQ3)

**タスク**: KB 全体から注入された矛盾を漏れなく・誤検出なく発見し、
食い違う出典まで特定する。

**データ**: クリーンな合成 KB(500 / 2000 トリプル)に矛盾を c ∈ {5, 20} 件注入:

- functional プロパティ衝突(同一主語に異なる値、出典を変えて記録)
- sameAs / differentFrom 衝突
- 推論を経てのみ衝突するもの(subClassOf 経由)を半数含める — LLM の目視走査が
  最も苦手とするはずのケース

provenance ログには注入時に相異なる `source` を記録しておく。

**条件**: B1(全トリプル+全出典ログを文脈で読ませて列挙させる)/
C1(メインがツールで走査)/ C2(kb-auditor へ委譲)。

**指標**: 矛盾検出の Precision / Recall / F1、出典ペア特定率、コスト。
KB 規模を上げたときの Recall の落ち方(B1 は文脈長で崩れる、が仮説)。

## 実験4: ハイブリッドコーディング (RQ4)

3つのサブ実験。いずれも Bash 確認をハーネスで自動 yes にする
(実験用の `can_use_tool` 差し替え。サンドボックス内で実行)。

### 4a. 境界バグの監査・修正

**データ**: 境界・オフバイワン・入力検証バグを植えた関数スイート 30 問
(ページネーション、区間演算、インデックス計算、日付、丸め)。
半数は既存の QuixBugs 系から翻案、半数は自作(隠しテストを別途保持)。

**条件**: 素のコーディングエージェント(ファイルツールのみ、= C1 から記号ツールを
除いた構成)vs `nsai code`(SMT あり)。

**指標**: バグ検出率、修正後の隠しテスト通過率、
smt_verify の反例がそのまま回帰テスト化された率(ツールログから)。

### 4b. テスト生成の変異検出力

**データ**: 正しい実装 20 関数(制約が明示的な数値・境界ロジック中心)。

**条件**: LLM 直書きテスト vs test-generator(反例・境界値・同値クラスの3系統)。

**指標**: mutation testing(mutmut)による **mutation score**。
境界変異(`<` ↔ `<=`、±1)に限定したスコアを別掲 — ここで差が付くはず。
テスト数を揃えた比較(上位 n 件)も併記し「数で稼いだ」への反論とする。

### 4c. loop-judge と完了判定

**データ**: 「全テスト成功+宣言済み主張の証明」が完了条件の修正タスク 15 問。
うち5問は**わざと完了不能**(仕様が矛盾)にして発散検出を試す。

**条件**: LLM 自身の「もう大丈夫そう」判定 vs loop-judge 委譲。

**指標**: 早期完了率(完了宣言時に隠しテストが失敗している率)、
完了不能タスクでの STALLED 検出率(vs 無限ループ/諦め)、平均イテレーション数。

## 副次実験 (RQ5, RQ6)

- **RQ5 コスト分析**: 実験2・3の C2 で、explorer/auditor を haiku → sonnet に
  変えた条件を追加。精度が同等でコストが数分の一、を示せれば
  「決定論的な地面の上では安いモデルで十分」という主張になる。
- **RQ6 code2kb**: OSS リポジトリ 3〜5 件(例: click, httpx 規模)に対し、
  (a) code2kb の import/呼び出しエッジと LLM 抽出(`ingest` にソースを渡す)の
  エッジ再現率を突き合わせ(ast 出力を正解系とする; LLM 抽出の網羅率が下がる
  ことを示す)、(b) 「関数 X を変更すると壊れうる呼び出し元は?」型の影響分析
  20 問を、構造層あり/なしで explorer に解かせ正答率を比較。

## 必要な実装

`experiments/` ディレクトリを新設(パッケージ本体には手を入れない):

| モジュール | 内容 | 規模感 |
|---|---|---|
| `kbgen.py` | 合成 KB 生成器(ドメインスキーマ、functional/sameAs/subClassOf 注入、QA ペア・矛盾・検証主張の同時生成、シード固定) | 中 |
| `harness.py` | 条件(B0/B1/C1/C2)×タスクの実行器。`build_options` を実験フラグ付きで呼び、構造化回答を抽出、JSONL に全測定項目を記録 | 中 |
| `grade.py` | 採点(EM、3値判定、P/R/F1)と統計検定(McNemar、paired bootstrap) | 小 |
| `bugsuite/` | 実験4のバグ植え込み関数+隠しテスト | 中(データ作成が主) |
| `report.py` | 集計表・図(劣化曲線、パレート図)の生成 | 小 |

先行して必要な本体側の小改修: `build_options` に「サブエージェント無効化」フラグ
(C1 用)と、実験ハーネスから `can_use_tool` を差し替えられる口。いずれも数行。

| 週 | 内容 | マイルストーン |
|---|---|---|
| 1 | kbgen + harness + grade 実装、実験1をパイロット実行(n=10)でプロンプト・抽出の穴を潰す | パイロット結果でメトリクス定義を凍結 |
| 2 | 実験1・2・3 本実行(sonnet 主系、5 run) | RQ1–3 の主結果表 |
| 3 | bugsuite 作成 → 実験4 本実行、RQ5 条件追加実行 | RQ4–5 の主結果表 |

## リスクと対策

- **OWL-RL 閉包の計算コスト**: `kb_verify` は毎回全閉包を計算する実装
  (`kb.py:closure`)なので 5000 トリプルで遅くなる恐れ。→ 週1で実測し、
  必要なら閉包キャッシュを入れる(実験結果には「システム改善」として書ける)
- **委譲不履行**: メインが委譲基準に従わず C2 ≒ C1 になる。→ 委譲率を必ず計測し、
  低ければ「委譲を強制した C2′」を追加条件にして上限性能と分離する
- **プロンプト感度**: ベースラインのプロンプトが弱いと批判される。→ B1 にも
  「段階的に推論せよ」「不明なら不明と言え」を入れた強化版を用意し、両方報告
- **採点の曖昧さ**: 自由回答の EM は表記揺れで壊れる。→ 回答を CURIE で
  返させる形式に固定(構造化出力)
- **合成データへの批判**: 外的妥当性は実験4(実コード)+ RQ6(実 OSS)で担保し、
  合成を選んだ理由(汚染・制御性)を本文で明示

## 論文構成案

1. Introduction — LLM の確率的推論と検証可能性の欠如、分業アーキテクチャの提案
2. System — KB/OWL-RL/CSP/SMT ツール層、サブエージェント委譲、code2kb(既存実装の記述)
3. Experiments — RQ1–4(主)、RQ5–6(分析)
4. Error Analysis — 誤りの層別(定式化 / 委譲 / ソルバー)。「誤りが定式化層に
   局在する」ことを quantify できれば本論文の一番強い知見になる
5. Related Work — GraphRAG、tool-augmented LLM、LLM+SMT(例: 形式検証支援)、
   self-verification 系
6. Limitations — 合成データ中心、単一 LLM ファミリー、閉世界の KB

投稿先候補: NeSy、AAAI/IJCAI(ニューロシンボリック枠)、または
ACL/EMNLP Findings(tool-augmented LLM 枠)。実験規模的には後者が現実的。
