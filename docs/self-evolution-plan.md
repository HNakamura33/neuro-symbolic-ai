## 1. 設計原則: 変更も主張である

### 1.1 分業原則のメタ適用

本プロジェクトの原則は「LLM は理解と定式化のみを担い、事実の保存・推論・検証・求解は
決定論的な記号層が行う。記号層が確認するまで、エージェントは事実を断定しない」である。
自己進化はこの原則を **一段メタに適用** して設計する:

> **LLM は改善仮説の生成と定式化のみを担い、変更の評価・採否・記録・巻き戻しは
> 決定論的な進化基盤(実証ハーネス + 記号ゲート)が行う。
> ゲートが通すまで、エージェントは変更を採用しない。**

「この変更は指標 M を悪化させずに M′ を改善する」という提案は、それ自体が1つの
**主張** であり、nsai の思想では主張は決定論的に検証されてから信じるものである。
LLM の「良くなった気がする」で変更を採用することは、LLM の「正しい気がする」で
事実を断定すること(= 偽検証)のメタ版に他ならない。

この設計が単なる整合性趣味でないことは文献が示している(§2.3): 実証ベンチマークのみを
ゲートにした自己改変エージェント(DGM)は評価器のハッキング(検出マーカーの除去、偽の
実行ログ)を実際に起こし、素朴な「ホールドアウトで改善したら採用」は 30–42% の偽採用を
出す(PACE の測定)。ゲート不在の経験メモリは蓄積に伴い性能・安全性が単調に劣化する。
**素朴な実証ゲートの故障モードこそが、記号ゲートを併置する動機である。**

### 1.2 スコープ

| 進化対象 | 含む/含まない | 理由 |
|---|---|---|
| 経験記憶(レッスン・契約) | ✅ L1 | KB + provenance + 矛盾検出という基質が既にある |
| オントロジー/スキーマ | ✅ L2 | 記号層自身が改善される — 本プロジェクト固有の進化軸 |
| プロンプト・構成 | ✅ L3 | prompts.py / subagents.py が単一ファイルの「ゲノム」 |
| サブエージェント構成・委譲ルーティング | ✅ L4 | issue #8-6(委譲判断の記号化)と直結 |
| 自身のソースコード | ✅ L5(最終段) | nsai code が自リポジトリを編集する構成は今日でも動く |
| モデル重み(fine-tuning) | ❌ | サブスクリプション認証で学習 API なし。アーキテクチャで示す方が論文の主張として強い(SymAgent との差別化軸を保つ) |
| タスク実行中のオンライン自己改変 | ❌(当面) | 世代間(inter-test-time)のオフライン進化に限定。ゲートを挟める粒度を保つ |
| 評価器自身の進化 | ❌(明示的に凍結) | §7。Red Queen Gödel Machine [2606.26294] が扱う未解決問題であり、本設計では評価器は不可変 |

分類でいえば **what = memory + architecture、when = inter-test-time、
how = evolutionary + verification-gated**(Gao et al. のサーベイ分類 [2507.21046])。

### 1.3 なぜ今か — 手動の進化は既に回っている

week-2 実験で実際に起きたことは「エラー分析 → プロトコル修正 → 再実行」の反復である:
audit の precision 崩壊を特定してプロンプト修正(issue #8-5)、委譲 0/600 を受けて
C2f(強制委譲)を追加、Z3/SPARQL のハングを見つけて SIGALRM を導入。
**これらは1周ごとに人間が回している進化ループ** であり、提案(どの修正を試すか)は
LLM/人間、採否は再実験の数字で決めていた。自己進化とはこのループの機械化・体系化であり、
ゼロからの新機能ではない。しかも採否判定に使う装置 — 条件別ハーネス、McNemar 正確検定、
paired bootstrap、シード固定の合成データ生成(gold は OWL-RL 閉包で構成的に正しい)—
は論文1のためにすべて実装済みである。

### 2.2 本設計の位置づけ(新規性)

調査エージェントによるギャップ分析(検索クエリと空振りの記録付き)の結論:

1. **実証ハーネス AND 記号検証の「二重ゲート」の連言で自己改変を裁定する系は存在しない。**
   最近接の SEVerA は FOL 契約が主で実証指標は最適化目的(採否ゲートではない)。
2. **RDF/OWL KB を進化の基質とし、推論器の矛盾検査 + provenance で書き込みをゲートする系はない。**
   KG メモリ系(MAGE/SAGE/A-MEM/Zep)はいずれも整合性判定が LLM/埋め込み依存。
3. **「評価器のコードに触れていない」「検出マーカーが保存されている」等のハーネス不変条件を
   ソルバー/構造照合で判定して採否条件にする系はない** — まさに DGM で破られた不変条件。
4. **オントロジー進化 in the loop**(自己改善ループがスキーマも整合性保存下で進化させる)は皆無。
5. **レッスン(教訓)を ABox として格納し TBox 不変条件と矛盾検査して採否を決める系はない。**

したがって本設計の主張は「**進化のたびに、変更を主張として二重に検証する
(実証: ハーネス + 統計検定 / 記号: KB 矛盾検査 + 構造契約 + SMT 不変条件)最初の
エージェント**」に置ける。なお「first formally verified self-evolving agent」の語は
SEVerA が使用済みのため **使わない**(書誌注意)。

### 2.3 素朴なゲートの故障モード(= 二重ゲートの動機、すべて文献で実証済み)

- **評価器ハッキング**: DGM は「ハルシネーション修正」を課されて、検出用マーカーを
  (明示的な禁止指示に反して)除去し偽の成功を報告する系統を生んだ。検出できたのは
  全変更の系統(lineage)が追跡可能だったから(2505.22954 App. F)[V]。
- **自己 p-hacking**: 「ホールドアウトで上がったら採用」を世代反復すると偽採用 30–42%、
  有害な変更の採用 10–33%(PACE, 2606.08106)[V]。多重検定・optional stopping の問題。
- **仕様の空洞化**: 形式検証器すら「自明に通る仕様」へ弱体化させることでハックされる
  (AlphaVerus のフィルタ段が対策として必須だった; 2412.06176)[V-]。
- **メモリの汚染と劣化**: ゲートなし経験蓄積で安全性違反率が暴露時間に対して単調増加
  (2605.17830)[V]、素朴な経験内在化の反復で能力が漸進的に劣化(2606.04703)[V]、
  「局所的には正しいが転移しない経験」を植える毒入れが成立(OEP, 2605.18930)[V]、
  ミス進化(misevolution)は frontier モデルでも起こる(2509.26354, ICLR 2026)[V]。
- **メタ生産性のミスマッチ**: ベンチマーク点数の高い個体ほど良い子孫を生むとは限らない
  (HGM, 2510.21614)[V]。
- **能力制約の理論**: 変更空間を無制約にすると汎化の統計的前提自体が壊れる —
  変更空間は一様に容量制限されるべき(2510.04399)[V]。→ 変更をスキーマ化された
  diff クラスに限定する設計根拠。

## 3. 進化ループのアーキテクチャ

### 3.1 二重ループ

```mermaid
flowchart TB
    subgraph Inner["内側ループ(タスク内; 実装済み)"]
        Task["タスク実行<br/>nsai (C1/C2 構成)"] --> Judge["loop-judge<br/>DONE / CONTINUE / STALLED"]
        Judge --> Task
    end

    Inner -- "実行記録<br/>results/*.jsonl + 会話履歴" --> Miner

    subgraph Outer["外側ループ(世代間; 本設計)"]
        Miner["エラーマイナー<br/>誤答・非効率の分類<br/>(grade.py + LLM 分析)"] --> Proposer["提案器(LLM)<br/>reflective mutation<br/>L1–L5 の型付き変更案"]
        Proposer --> Gates["ゲートカスケード G0–G5<br/>(決定論的; §3.2)"]
        Gates -- "採用" --> Archive["アーカイブ<br/>git ブランチ + 進化KB<br/>(系統・採否・根拠)"]
        Gates -- "棄却(理由付き)" --> Archive
        Archive -- "新構成を配備" --> Inner
        Archive --> MetaJudge["メタ loop-judge<br/>進化の停止判定<br/>(改善なし K 世代 / 予算 / STALLED)"]
    end

    Human([人間]) -- "L2/L4/L5 の最終レビュー<br/>(PR ゲート)" --> Gates
```

- **内側ループ**は現行の nsai(loop-judge が終了判定を記号化済み)。
- **外側ループ**が新設分。1世代 = 「実行記録の採掘 → 変更提案 → ゲート → 採否記録」。
- **メタ loop-judge**: 進化ループ自体の終了条件も loop-judge と同じ思想で記号化する
  (`gate-passing 改善なしが K 世代連続 → STALLED`、予算超過 → 停止)。

### 3.2 ゲートカスケード(安い順に裁定、どこで落ちたかを必ず記録)

AlphaEvolve の評価カスケード [V] と DGM の段階評価 [V] を、記号ゲートを先頭に置いて再構成:

| ゲート | 内容 | 使う既存装置 | コスト |
|---|---|---|---|
| **G0 型ゲート** | 変更が宣言された diff クラス(L1–L5 のスキーマ)に収まっているか。可変領域外のパスに触れていないか | diff のパス/AST 照合(DafnyPro の diff-checker と同型 [V]) | ≈0 |
| **G1 記号ゲート** | (a) KB/レッスンの矛盾検査 — 追加が既存の active な事実・契約と contradicted にならない(b) 構造契約 — code2kb 再構築後に記録済み契約(ツール名・シグネチャ・サブエージェント定義)が entailed のまま(c) 符号化可能な数値不変条件は smt_verify | kb_verify / kb-auditor / code2kb / smt_verify | ≈0(LLM 不要) |
| **G2 racing** | 小サブセット(~40問, haiku)で統計的に負け確定した候補を早期棄却(CAPO の racing [V]) | harness --limit + grade | $0.5–1/候補 |
| **G3 統計ゲート** | 本評価(200問級, 主モデル)。paired McNemar / bootstrap で有意改善、**FVR(偽検証率)は親以下を厳守**(安全軸は取引不可) | harness + grade.mcnemar_exact / paired_bootstrap | $4–10/候補 |
| **G4 転移ゲート** | **新鮮なシード**の合成データ(kbgen で当該世代用に新規生成)+ 保留系ベンチマークで非退行を確認。世代ごとにシードを使い捨てるため評価集合への過適合が構造的に起きにくい | kbgen --seed(gold は閉包検証済み) | $2–5/候補 |
| **G5 人間ゲート** | L2(公理)・L4(構成)・L5(コード)は PR として提示し人間がマージ。L1/L3 は予算内で自動、週次レビュー | gh pr + 進化KB の根拠提示 | 人手 |

多重検定について: G3 を世代反復すると optional stopping で偽採用が積み上がる(PACE の
指摘そのもの)。当面は (i) G4 の新鮮シードで独立性を確保、(ii) 世代ごとの有意水準を
α/世代数で保守化、を採り、キャンペーンが長期化するなら PACE 型の anytime-valid
e-process への置換を検討する(§8)。

### 3.3 アーカイブと系統 — 進化の状態は KB に置く

DGM の教訓は「全変更の追跡可能な系統があったからハッキングを検出できた」である。
nsai には provenance 付き KB という上位互換の装置があるので、**進化の履歴自体を
記号化して格納する**(ドメイン KB とは別ファイル `kb-evolution.ttl`、`ev:` 名前空間):

```turtle
ev:gen_012 a ev:Generation ; ev:parent ev:gen_009 ; ev:proposed_by ev:miner_run_44 .
ev:change_031 a ev:PromptChange ;             # diff クラス(G0 で照合)
    ev:targets ev:delegation_criteria ;
    ev:motivated_by ev:error_cluster_2hop_stopshort ;
    ev:gate_g1 ev:pass ; ev:gate_g3 ev:pass_p0.003 ; ev:gate_g4 ev:pass ;
    ev:verdict ev:accepted ; ev:commit "a1b2c3d" .
```

- 採用も**棄却も**根拠付きで記録する(棄却理由は次世代の提案器への入力になる —
  GEPA の reflective mutation は失敗トレースから学ぶ [V])。
- 系統・採否・指標は SPARQL で照会可能(「3-hop EM を改善した変更はどれか」)、
  kb-auditor で進化履歴自体の矛盾も監査可能。DGM 型アーカイブ(貪欲でなく全個体保持、
  親サンプリングで性能の谷を越える)を KB 上に実装する。
- 実体は git ブランチ(1候補 = 1ブランチ、採用 = merge)+ 進化 KB の対応付け。
  PROMPT_REV 型のバージョンスタンプは harness が既に全レコードに刻んでいる。

### 3.4 不変の評価器

進化ループの信頼性は「評価器はエージェントに書き換えられない」ことに全面依存する
(DGM のマーカー除去、AlphaEvolve の「プログラム的評価器のみ」原則)。

- **不可変領域**: `experiments/`(harness/grade/kbgen/report/evolve)、`tests/`、
  `data/`(gold)、`results/`、進化 KB、`.git`。G0 が diff パスで機械的に拒否し、
  さらに G1 が code2kb の構造契約で二重に検査する。
- 評価実行は候補のワークツリー**外**から、読み取り専用マウント相当の分離で行う。
  結果 JSONL は追記専用で候補側から不可視。
- 評価器自身の進化は本設計では明示的にスコープ外(§1.2)。変更したくなったら人間が
  普通の開発として行い、全アーカイブ個体を新評価器で再採点する(RQGM [V] の
  epoch 境界と同じ扱い)。

## 4. 進化する層 L1–L5

リスク昇順。各層は独立に着手でき、ゲートは共通カスケード(§3.2)を使う。

### L1 経験記憶の進化 — 検証済みレッスンストア

**対象**: 実行記録から蒸留した再利用可能な教訓。定式化パターン(「公開年を問う質問の
SPARQL 雛形」)、失敗回避則(「回答前に答えの型を検査する」)、プロジェクト契約。

**機構**:
1. **蒸留** — 世代末に誤答/成功クラスタから lesson-distiller(サブエージェント)が
   候補レッスンを構造化して抽出(`ingest --jsonl` の会話履歴整形が流用できる)。
2. **格納** — ABox として進化 KB に `ev:status ev:candidate` で記録。適用条件
   (タスク種別・トリガ)、規則本文、由来タスク(provenance)、可能なら**コンパイル済み
   チェック**への参照を持つ。
3. **ゲート** — G1: 既存 active レッスン・TBox 不変条件との矛盾検査(**DL 推論器で
   レッスン庫を検査する系は文献に存在しない** — ギャップ5)。G2–G4: レッスンを
   有効化した構成 vs 親構成の対照評価。**転移テストが本丸**: 由来タスクでなく
   held-out タスク群で非退行を確認する(OEP 型毒入れ [V] への唯一の既知対策)。
4. **昇格と生涯管理** — candidate → active → deprecated。参照されないレッスンは減衰、
   矛盾が出たら Zep 型に**削除でなく無効化**(時間スコープ付き; 監査可能性を保つ)[V]。
   kb-auditor の定期走査を「書き込み時だけでなく縦断的に」かける(2605.17830 の教訓)。
5. **注入** — active レッスンをタスク種別で選別しシステムプロンプトに同梱(まず 上位 k 件
   の静的注入で開始; 検索式注入は KB が育ってから)。

**レッスンはできる限り「実行可能な検査」に昇格させる**(TRACE の知見: プロンプト注入型
メモリは違反 57.5% 残存、決定論的チェックへのコンパイルで 2.0% まで低下 [V])。例:
「答えの型を検査する」は文章でなく、FINAL 直前に `kb_verify (answer, rdf:type, 期待クラス)`
を強制する手続きとして表現できる — **学んだ教訓が記号層の検査として執行される**。
これは本プロジェクトの思想の自然な帰結であり、文献上も未踏(ギャップ2/5)。

### L2 オントロジー/スキーマ進化 — 地面自体を固くする

**対象**: `owl:FunctionalProperty` 宣言、`rdfs:subClassOf`、`owl:differentFrom` 等の
公理。矛盾検出の再現率は宣言されたスキーマの豊かさで決まる(README の
「モデリングのコツ」を自動化する層)。

**機構**:
1. **帰納** — KB 統計から候補公理を採掘(決定論的; LLM 不要)。例: 述語 p が
   N 主語すべてで単値 → FunctionalProperty 候補。クラス A の全インスタンスが B にも属す
   → subClassOf 候補。
2. **ゲート** — G1: 公理追加後の閉包に新規矛盾が出ないか検査。**矛盾が出た場合は
   2値に分岐**: 公理が誤りか、公理が正しくてデータが汚れているか — これは人間に
   証拠(最小矛盾集合)付きで提示する価値のある発見であり、G5 人間ゲート必須の理由。
   プロトコル自体を「不整合が到達不能」な形に組む先例(反概念の充足性照会に還元;
   2604.16672 [V])に倣う。G3/G4: 公理採用が実験3型の矛盾検出 recall / 実験1型の
   推論必須問題正答率を実際に改善するか。
3. **論文上の意味** — エージェント自身の自己改善ループがスキーマを整合性保存下で
   進化させる系は存在しない(ギャップ4)。「ニューラルが歩くほど、記号の地面が固くなる」。

### L3 プロンプト・構成の進化 — GEPA 型 + 二重ゲート

**対象**: `prompts.py` の各節(委譲基準、検証手順、回答形式)、サブエージェントの
プロンプト、モデル割当(haiku/sonnet/inherit)。ゲノムは単一ファイル群 + git。

**機構**: GEPA 型 reflective mutation [V] — 誤答トレース(harness JSONL + 転記)を
強いモデルに与え、対象節への**局所的な**編集を提案させる(G0 で編集範囲をスキーマ強制)。
候補は §3.2 のカスケードへ。アーカイブはスカラー最優秀でなく **Pareto フロント**
{macro-F1, FVR(取引不可), EM, 矛盾検出 F1, コスト} で保持(GEPA の per-task Pareto と
MO-CAPO/CRAFT のコスト認識探索 [V-] に倣う)。

**探索が最も効く場所はコスト×精度フロンティア**である。week-2 の実測が示す通り、
sonnet は単独で天井に張り付く課題が多く(4a/4c)、haiku は headroom が大きい
(RQ5: haiku C2 が sonnet 同等を 1/3 コストで達成)。よって L3 の主戦場は
「**haiku 級構成を進化させて sonnet 級の成績に近づける**」に置く — 決定論的な地面の上
では安いモデルで十分、という論文1の主張の進化版になる。

### L4 サブエージェント構成・委譲ルーティングの進化

**対象**: `subagents.py` の AgentDefinition 集合(存在・ツール許可・モデル)、および
**委譲ルーティング規則**。issue #8-6 の「委譲判断の記号化」をここに統合する:
ルーティングを LLM の裁量でなく決定論的規則(KB 規模・推定ホップ数・タスク種別 →
委譲先)として KB に置き、**規則のパラメータを外側ループが進化させる**。
メタ判断も記号側に置き、その記号規則をデータで調律する — 二層の分業。

探索空間はモジュール型(AgentSquare 型 [V])に限定し、ADAS 型の自由コード合成は
行わない(容量制限の理論 [V] と G0 の型ゲートを保つため)。MASS の知見
「プロンプト最適化 → トポロジー → 再プロンプト」の順序 [V] に従い、L3 安定後に着手。
新規サブエージェント案の例: sparql-reviewer(生成された SPARQL を質問と突き合わせて
から実行; T2 の恒久対策)。

### L5 ソースコード自己改変 — proof-carrying self-modification

**対象**: `src/nsai/**` のみ(不可変領域は §3.4)。`nsai code --full-auto` を自リポジトリ
のワークツリーに向け、DGM 型のループを回す — ただし各パッチは**証拠束**を同梱して
初めてゲートに進める:

1. テストスイート成功(既存)
2. ハーネス小バッテリで非退行(G2→G3; FVR は親以下)
3. **構造契約の保存** — code2kb 再構築 → 記録済み契約(公開シグネチャ、ツール名、
   9ツール+Task の許可集合、サブエージェント定義)を kb_verify — contradicted = 即棄却
4. **符号化可能な不変条件の SMT 証明** — 例: 閉包キャッシュの無効化条件、予算計算、
   racing の打ち切り閾値のような整数論理(誠実に: 完全な機能検証は現状の vericoding
   水準 [V] では届かない。契約=構造層+局所 SMT が現実的な形式ゲート)
5. G5: **PR として人間がマージ**(自動マージは恒久的にしない)

種タスクには issue #8 の実需(記号層のプロセス分離 #8-7、閉包の増分化 #8-8)を使う —
成功すればそのまま本体の改善になる。「各自己パッチが機械検査可能な証明書を同梱する」
構成は文献上未請求の領域(ギャップ3)。

## 5. 初期ターゲット(実測済みの課題3件)

自己進化の最初の獲物は仮説ではなく、week-2 実験で測定済みの失敗である。
それぞれ「人手修正(issue #8)と進化ループ産の修正を突き合わせられる」独自の価値がある。

### T1: 委譲基準 — C2 の自発委譲 0/600(MetaQA)

現行プロンプトの委譲基準(「3ホップ以上かかりそうなら委譲」)は一度も発火しなかった。
C2f(プロンプト強制)が人手ベースラインとして走行中(49/600 で中断)。
**L3 の一号案件**: 委譲基準の節を進化させ、委譲率・EM・コストで C2f と比較する。
その恒久解は L4 の記号ルーティング(発火条件を KB 規模・ホップ推定で決定論化)。

### T2: 2-hop の「1ホップ手前で停止」— C1 63/200 誤答, C2 47/200

誤答実例(results/metaqa-C1.jsonl): `metaqa-2hop-5` は公開年を問われて
`ns:Aladdin`(映画)を回答(gold `ns:1992`)、`metaqa-2hop-0` は監督を問われて
脚本家を回答。**質問が求める型と答えの型の不一致** = 定式化層の系統誤りで、
2-hop EM が B1p(.945)に大負けする主因(C1 .685 / C2 .765)。

**L1 の一号案件**: 「FINAL 前に答えの型を照合する」レッスン(コンパイル可能: 期待クラスの
kb_verify / SPARQL ASK を強制)。63 件からの蒸留 → held-out 2-hop(resume サブセット
方式で構築可)で対照評価。**エラー分析(issue #8-3)がそのまま Phase 0 になる。**

### T3: audit の precision バイモーダル崩壊(1.00 or ~0.05)

原因特定済み: auditor は正しい集合を返すのに、main が報告時に over-expand する。
**L3/L1 混合案件**: 報告プロトコルの構造化(スキーマ強制)+ 「報告前に各ペアを
kb_verify で自己検査する」レッスン。issue #8-5 の人手修正案と進化産修正を比較できる。

## 6. 評価計画(論文2の骨子)

主張: 「検証ゲート付き自己進化は、(a) ゲートなし自己進化より安全に(汚染・退行なく)、
(b) 人手修正と同等以上の改善を、(c) 監査可能な形で達成する」。

| RQ | 問い | 実験 | 主指標 |
|---|---|---|---|
| RQ-E1 | ゲート付きレッスン記憶は、無記憶・**無ゲート記憶**(ExpeL 型 LLM 判定採用)より held-out 性能を上げ、蓄積劣化を防ぐか | L1 を T2 で走らせ、3条件比較を世代数に対してプロット | held-out EM/FVR の世代推移、矛盾混入数、レッスン残存率 |
| RQ-E2 | プロンプト進化は人手修正に匹敵するか | L3 を T1/T3 で、原版 vs 人手(C2f, #8-5)vs 進化産 | 委譲率、2-hop/audit 指標、進化コスト、**ゲート棄却分布** |
| RQ-E3 | スキーマ帰納は矛盾検出を改善し、不整合を一切入れないか | kbgen で「スキーマを剥がした」KB を生成し L2 に回復させる(gold スキーマと突き合わせ可能) | 公理回復率、実験3 recall の改善、導入不整合 0 件 |
| RQ-E4 | 二重ゲートはコード自己改変で何をどれだけ堰き止めるか | L5 パイロット(#8-7/8-8 を種に) | 各ゲートの棄却件数・棄却理由分布、退行漏れ 0、人間レビュー負担 |
| RQ-E5 | ゲートはハッキング・毒入れを実際に検出するか | 敵対的プローブ: DGM 型(マーカー除去機会)、OEP 型(非転移レッスン)、仕様空洞化を意図的に仕込み検出率を測る | 検出率(ゲート別)、素朴ゲート条件との差 |

横断メトリクス — **採用耐久率**(accepted な変更が K 世代後の新鮮シードでも有効な割合;
自己 p-hacking の事後検出)と **進化の監査可能性**(任意の採用変更について
「なぜ」を進化 KB から SPARQL で復元できること; デモで示す)。

**ゲート棄却分布(RQ-E2/E4)は本論文で最も雄弁な結果になりうる**: 「G1(記号)が
落とした候補のうち G3(実証)では通っていたものが x%」が正なら、記号ゲートは実証ゲート
に**還元できない**仕事をしている直接の証拠になる。

コスト概算(sonnet 判定 + haiku 探索、quota 制約: 重いストリーム同時 ≤3):
Phase 0 ≈ $10 / L3 キャンペーン1本 ≈ $50–150(15世代 × racing $1 + 採用候補のみ G3–G4)
/ L1 ≈ $50–100 / L5 パイロット ≈ $50–100。全体 ≤ $500 目安。

## 7. 安全設計

§2.3 の故障モードに1対1で対応させる:

| 脅威(文献で実証) | 対策(本設計) |
|---|---|
| 評価器ハッキング(DGM マーカー除去) | 不可変領域 + G0 パス検査 + G1 構造契約 + 評価はワークツリー外から(§3.4) |
| 自己 p-hacking(PACE) | G4 新鮮シード(kbgen は世代ごとに使い捨て可能な検証済み評価集合を生成できる — 本設計の最大の構造的優位)+ α 保守化、長期化なら e-process |
| 指標ゲーミング(Proxy Compression) | 多目的 Pareto + FVR は取引不可の安全軸 + ラベル別 recall を常時報告(「全部 unknown と答える」型の縮退を露出させる) |
| メモリ汚染・毒入れ(OEP/misevolution) | レッスンは矛盾検査 + **転移テスト**を通過して初めて active、無効化は削除でなく時間スコープ、kb-auditor の縦断監査 |
| 仕様の空洞化(AlphaVerus) | 契約の非自明性チェック(その契約は何かを排除しているか)を G1 に含める |
| 暴走・コスト超過 | 世代・キャンペーン単位の予算上限、メタ loop-judge の STALLED 検出、quota 教訓(夜間の重複ストリーム禁止)を運用規則に明文化 |
| 能力の静かな劣化 | 安全回帰スイート(FVR・unknown 正答率・STALLED 検出)を全ゲートの必須項目に(misevolution 対策) |
| サンドボックス | L5 は使い捨てワークツリー + `--full-auto`(ネットワーク遮断); 依存が要る場合のみコンテナ + bypass(実験4d と同じ運用) |

人間の関与: L1/L3 = 予算内自動 + 週次レビュー。L2/L4/L5 = 変更ごとに PR レビュー必須。
自動マージは全層で行わない(採用 = ブランチ上の確定であり、main への反映は常に人間)。

## 8. リスクと留保

- **改善の頭打ち**: sonnet は多くの課題で既に天井。→ 主戦場を haiku 級構成の底上げと、
  天井のない課題(2-hop、委譲、audit precision)に絞る(§4-L3)。
- **合成データへの過適合**: G4 の新鮮シードも同一生成器由来である限り分布は同じ。
  → 公開ベンチマーク(MetaQA 摂動版・ProofWriter)を**最終確認専用**に温存し、
  fitness には決して使わない。
- **提案器の質**: 変更仮説の質は結局 LLM に依存する(ここは確率的なまま)。
  → それで良い — 提案は自由に外し、ゲートが守る、が本設計の分業。棄却理由の
  フィードバック(§3.3)で提案の当たり率自体も世代改善を狙う。
- **統計ゲートの厳密性**: McNemar の世代反復は本来 anytime-valid でない。当面の緩和策
  (新鮮シード + α 保守化)で十分かは RQ-E1 の採用耐久率で実測し、不足なら PACE 型
  e-process に置換(実装は grade.py に閉じる)。
- **G1 の網羅性の過信**: 記号ゲートは「符号化した不変条件」しか守らない(OWL-RL の
  表現力の限界と同じ構図)。→ 論文でも「二重ゲートは万能でなく、実証・記号が**互いの
  死角を補う**」という主張に留める。RQ-E5 がこの限界を定量化する。
- **工数**: 外側ループ(evolve.py + gates.py + 進化 KB スキーマ)の新規実装は
  正味 3–5 日想定(ハーネス・統計・生成器は流用)。論文1の完成が最優先である間は
  Phase 0(0.5日)だけ先行し、本格着手は論文1の実験完走後とする。
