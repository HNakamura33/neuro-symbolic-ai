## 概要(Abstract)

産業応用の LLM エージェントは知識ベース(KB)を蓄積・運用するようになっており、その KB を下流で信頼する前に内部矛盾の監査が必要になる。自然なニューロシンボリック設計は、エージェントに古典的推論器 — 本研究では RDF KB 上の OWL-RL 前向き連鎖閉包 — へのアクセスを与え、制約違反を報告させるものである。本稿では、この設計の実務上見過ごされがちな失敗モードを報告する: **既に矛盾を含む KB の上で健全な推論器を走らせると、矛盾が静かに増幅される**。我々の監査ベンチマークでは、functional property 違反が `owl:sameAs` 連鎖と相互作用し、閉包が 19 件の真の違反を 95 件の見かけの違反に膨張させ(より大きなグリッドでは 20 件が 393 件に)、エージェントの報告 Precision は 0.05 に沈んだ — しかも run 間の予測はビット単位で同一だった。エージェントは決定論的だが汚染された推論器出力を忠実に転記していたのである。報告をトリプル単位の provenance 照会で修復する戦略は、1 グリッドで 318 回のツール呼び出しと $15.51 を要してなお Recall 0.60 で頭打ちだった。我々の修正はモデリングではなく工学的なものである: 開放的な閉包アクセスを、**閉包前の主張トリプル上で**違反を列挙し、各違反に provenance を同梱して 1 回で返す専用ツール `kb_violations` に置き換えた。修正後、同一のエージェントが全 4 グリッド × 単一/委譲構成 × 各 3 runs で Precision・Recall 1.0 を達成し、コストは 1 run 約 $15 から約 $0.2 に低下した。この経験を「推論の前に監査せよ・推論由来トリプルにタグを付けよ・全ての判定に provenance を添えよ・LLM 出力は決定論的検査でゲートせよ」というデプロイレシピに蒸留する。マルチホップ QA での対の実験(記号的な回答検査器を任意ツールでなく必須ゲートにすると精度 0.79 → 0.97)も同じ設計テーゼを支持し、さらにネガティブコントロールが「決定論性こそが本質」であることを示す: 決定論的検査を LLM 判定者に置き換えると、誤った完了宣言は統計的に変わらない(p = 0.09)— 同じモデル系列の判定者は、エージェントが失敗する場面で同じように失敗するからである。

## 1. はじめに

- **背景。** 構造化知識を蓄積・活用する LLM エージェントが本番投入されつつある(エージェントメモリエンジン、企業 KG コパイロット)。KB を検索・計画・コンプライアンスに使う前に、誰かが「この KB は内部整合的か、そうでないなら正確にどの主張が衝突しているのか」に答えねばならない。これが監査タスクである。
- **自明な NeSy 設計。** エージェントに古典的推論器をツールとして与える: OWL-RL 閉包を計算し、functional property / disjointness の違反を照会し、報告させる。決定論的推論こそ LLM に欠けているものであり、これは教科書どおりのニューロシンボリックな分業である。
- **落とし穴。** 古典的推論器の健全性は「KB がその意味論が成立する程度に無矛盾である」という前提の下でのみ成り立つ。監査対象の KB は構成上その前提を**満たさない** — それこそが監査する理由である。したがって先に閉包を走らせることは推論器を契約外で使うことであり、LLM の消費者にとって最悪の形で壊れる: 自信に満ち、内部整合的で、決定論的な大量のゴミを生成し、LLM にはそれを疑う根拠がない。
- **貢献。**
  1. 産業的失敗モードの特定: 閉包による疑似違反の増幅(「推論器の中毒」)と、その機構レベルの診断(閉包出力の逐語転記; §3)。
  2. 工学的修正 — `kb_violations`: 主張トリプル上の閉包前列挙+provenance 同梱 — により全グリッドで P/R 1.0 を回復し、コストを約 75 分の 1 に削減(§4)。
  3. 修正を一般化したデプロイレシピ: LLM 出力経路上の必須ゲートとしての決定論的検査。マルチホップ KGQA(0.79 → 0.97)で二重に検証(§5)。
  4. ゲートの有効成分が*決定論性*であることを単離するネガティブコントロール: 完了宣言に対する LLM loop-judge は矛盾仕様での誤宣言を有意に減らせず(p = 0.091)、モデル能力が支配的(p = 2.9e-08)で、合成含意型の矛盾は強いモデルを両プロトコルとも破る(§6)。

## 2. システムとタスク

- **システム。** LLM エージェント(Claude Sonnet 級)+永続 RDF/OWL KB へのツール群: `kb_find`、`kb_sparql`、`kb_verify`、`kb_infer`(`owlrl`/`rdflib` による OWL-RL 閉包)、`kb_provenance`(トリプル毎の出典照会)。委譲構成(C2)は symbolic-explorer サブエージェントを起動でき、C1 は単一エージェント。ベースライン B1 は KB 全文を文脈に貼る。
- **監査ベンチマーク。** 2×2 グリッドの合成 KB — {500, 2000} 主張 × {5, 20} 個の注入矛盾(`a500c5` … `a2000c20`)。注入矛盾はすべて正解既知の functional property / disjointness 制約違反。指標はエージェントの報告集合の注入集合に対する Precision/Recall。各セル 3 runs。
- **修正前の結果。** B1(KB 全文)はこの規模では全 12 runs で P=R=1.00($0.7–2.2/run)。直感に反し、記号ツール条件は*双峰的*だった: C1 は 12 runs 中 7 で、C2 は 4 で P ≈ 0.05 に崩壊(Recall はほぼ 1.0 のまま)。監査を信頼可能にするために足した記号層こそが、信頼できない報告の発生源だった。

## 3. エラー分析: 健全な推論器はいかにして監査を汚染するか

失敗 run の全数分析(予測は人間の判断でなく KB と機械的に突き合わせ)により機構を特定した:

- **閉包増幅。** `a500c5` の基底 KB には主張レベルの違反が 19 件ある。OWL-RL 意味論の下では functional property 違反が衝突オブジェクト間の `owl:sameAs` を含意し、この sameAs が連鎖(導出 281 ペア)、代入により閉包にのみ存在する 95 件の*見かけの*違反が製造される。大きいグリッドでは 20 件が 393 件に膨張した。Precision 20/393 ≈ 0.05 は LLM の「幻覚」ではない — 報告された項目はすべて推論グラフに実在する。
- **逐語転記。** 失敗 run の予測集合は **run 間・C1/C2 間でビット単位に同一**だった。エージェントは NeSy の教義どおりのこと — 決定論的推論器に従いその出力を写すこと — を正確にやっていた。決定論は誤りを封じ込めるどころか増幅した。P=1.00 を取った run は、`kb_infer` を一度も呼ばなかったか、その出力を `kb_provenance` で濾過した run に他ならない。
- **provenance による修復はスケールしない。** 部分的に機能した唯一の戦略 — 候補違反を 1 トリプルずつ provenance 照会で確認 — は `a500c20` で 318 回の呼び出しと $15.51 を要し、エージェントが諦めるまでに R=0.60 にしか達しなかった。トリプル単位の修復ループは仕事の形が間違っている。
- **実務者への教訓。** 故障は LLM にも推論器にも KB にもない。*合成*にある: 前提条件(無矛盾性)がタスクそのものによって破られる推論ツールを、その前提を検査できない消費者(LLM)に晒したことにある。

## 4. 修正: 閉包の前に列挙し、判定に provenance を同梱する

開放的な推論器アクセスを専用監査ツールに置き換えた(プロンプト/ツール改訂 4):

- **`kb_violations`**: functional property / disjointness 違反を**主張トリプルのみの上で、いかなる閉包よりも前に**列挙し、各違反を根拠トリプルとその provenance レコードと共に 1 回の呼び出しで返す。318 回の修復ループが 1 回のツール呼び出しになる。
- **asserted/inferred タグ**: `kb_infer` 実行後の `kb_find`/`kb_sparql` の結果に `asserted` / `inferred` のタグを付け、閉包出力が基底主張になりすませないようにする。さらに `kb_infer` は KB が制約違反を含む場合にカスケード警告を発し、この KB 上の閉包は監査級の証拠ではないことをエージェント(とログの読者)に伝える。
- **結果。** rev4 で監査ベンチマークを再走: **全 4 グリッド × {C1, C2} × 3 runs で Precision・Recall 1.0** — 24/24 runs、双峰性消失 — コストは provenance 修復戦略の **$15 に対し約 $0.2/run**。エラー分析 → 局所的設計変更 → 同一ベンチマークでの完全回復という一巡は、ツール 1 個の実装のみで、モデル変更もプロンプト戦略の変更も(新ツールの説明以外)不要だった。
- **なぜこれが正しい形か。** この修正は監査の意味論を決定論層の*内側*に移し(何を違反と数えるかをツールが決め、provenance で証明する)、LLM の仕事をオーケストレーションと報告整形 — もともと正しくできていた部分(Recall は一度も問題でなかった)— に縮小する。

## 5. 同じ原理の第二領域: マルチホップ QA のゲート化

監査の修正は一般原理の具体化である: **決定論的検査は任意ツールとしてはほとんど役に立たず、出力経路上の必須ゲートとしては劇的に効く。** これを MetaQA(133,582 トリプル KB、600 問、1/2/3-hop、完全一致)で独立に検証した:

- 記号 KB ツールを*使用可能だが任意*とした場合、精度 **0.790** — 記号ツールを一切持たない純粋な agentic-grep ベースライン(**0.860**)を下回る。
- 2 つのゲート — `kb_check_answer`(候補解が KB に実在し、質問と型が整合し、起点エンティティの自明な属性でないこと)と verify-before-FINAL プロトコル(最終ホップのトリプルが `kb_verify` を通らない限り解答不可)— を追加すると精度は **0.970**(hop 別 0.950/0.980/0.980)。McNemar: 対 grep ベースライン 66/0 判別対、p = 2.7e-20; 対 任意ツール条件 108/0、p = 6.2e-33。
- ゲートの上にさらに決定論的経路走査(`kb_path`)を足す ablation は 0.962 で、ゲートのみと有意差なし(10/5、p = 0.3): **天井を決めているのはゲートであり、探索の記号化は何も足さない。**
- 過去に失敗した 126 タスクのみをゲート付きプロトコルで再走すると 106/126(84%)が回復し、同数 126 タスクの対照群での退行は**ゼロ** — 監査と同じ「分析 → 修正 → 検証済み回復」の一巡である。

両領域で勝ち筋は同一だった: LLM に記号層を参照するかどうかを*選ばせる*のではなく、記号検査を出力の前提条件にすることである。

## 6. ネガティブコントロール: LLM 判定者はゲートではない

§5 への当然の反論がある: 「追加の検証ステップなら何でも効くのではないか。ゲートの利得は検査が決定論的だからではなく、単に『二度見』するからではないか」。これを第三のタスク族 — コード修正の完了宣言 — で直接検定した。追加の検証者が記号検査ではなく**別の LLM** である場合を測るのである。

- **セットアップ。** 小さな Python 修正タスク 50 問(仕様+実装+隠しテスト)。うち 20 問は意図的に矛盾した仕様(実行不能)で、3 つの難度層に層化: *direct-example*(2 つの要件が同一の明示入力に異なる出力を割り当てる)、*rule-vs-example*(ワーク例が明記された規則に反する)、*implied*(単独では健全な 2 規則が特定入力でのみ衝突する)。エージェントは `FINAL: DONE` か `FINAL: STALLED` で終える必要があり、実行不能仕様での正解は STALLED。条件は **self**(エージェント自身が完了を判定)vs **judge**(loop-judge サブエージェントが全宣言を承認)。*誤宣言* = 隠しテストが失敗したままの DONE 宣言。実行不能性は機械検証済み(全実行不能タスクの隠しケースに同一入力・異期待値のペアが最低 1 組)。
- **結果: LLM 判定者は誤宣言を有意に減らさない。** Haiku 級モデルでは self が実行不能 20 問中 19 問で誤宣言、judge は 15/20(片側 Fisher p = 0.091、n.s.)。direct-example 層では judge が self より*悪い*(5/5 vs 4/5)。Sonnet 級では self と judge は区別できない(2/20 vs 3/20、p = 0.83)。実際に支配的なのはモデル能力である: 同一プロトコル下でモデル間 19/20 vs 2/20(p = 2.9e-08)。
- **subtle な層は強いモデルも破る。** implied 層では Sonnet 級モデルすら 2/5 で誤宣言 — しかも*両*条件で。判定者は救えない。
- **考察。** 判定者は同じモデル系列から取られ、同じ仕様を読む。したがってその誤りはエージェントの誤りと**相関**する — 同じ誤り分布からの 2 回目のサンプルであって、直交した検査ではない。判定者が効いた場面(Haiku の rule-vs-example、2/5 vs 5/5)の機構は「仕様全体の読み直し」であり、それは厳密性ではなく多様性の利得である — そして多様性は保証には積み上がらない。これこそ、決定論的ゲートが回避する LLM 自己検証の構造的弱点である: KB 所属検査やソルバの判定は、LLM とは*独立な*誤りモデルを持つ。特筆すべきは、今回の矛盾仕様が小さな算術的契約であることだ: 要件の連言は SMT ソルバにとって機械的に UNSAT である。仕様→SMT ゲート(制約集合が充足不能なら STALLED を宣言)は、このネガティブ結果の構成的対応物であり、今後の課題とする。

## 7. デプロイレシピ

LLM エージェントと KB・古典推論器を組み合わせるチームへ:

1. **推論の前に監査せよ。** 矛盾検出の一工程として閉包/実体化を走らせてはならない。違反は主張トリプル上で列挙し、推論器の無矛盾性前提は「仮定」ではなく「検査すべき入力契約」として扱う。
2. **推論由来トリプルにタグを付けよ。** 閉包出力を返しうる全てのクエリ面にラベルを義務付ける。LLM は主張された事実と含意された事実を自力で区別できず、与えられた方をそのまま転記する。
3. **判定と provenance を 1 回の呼び出しで同梱せよ。** トリプル単位の provenance 修復ループは 1–2 桁高コストでなお損失がある。監査ツールは(違反, 根拠, 出典)を一体で返すよう設計する。
4. **提供ではなくゲートせよ。** 出力経路上の決定論的バリデータ(回答検査器、verify-before-final)は、同じバリデータを任意ツールとして提供する場合に勝る — 我々の QA 実験では任意版は*記号ツールなしにすら負け*、ゲート版は全てを制した(0.79 vs 0.86 vs 0.97)。
5. **回復は対照群で検証せよ。** 失敗タスクの再走には、退行ゼロを保証するための同数の非失敗対照群が要る(我々の場合: 106/126 回復、0/126 退行)。
6. **ツール出力を逐語でログせよ。** run 間でビット同一の予測集合こそが、故障を LLM でなく推論器に局在させた決定的証拠だった。生のツール出力ログがなければ、この故障は確率的幻覚に見えたはずである。
7. **ゲートは決定論的でなければならない — LLM 判定者はゲートではない。** 同じ系列の判定者モデルは同じ誤り分布からの 2 回目のサンプルである: 完了宣言の実験で誤宣言は統計的に不変(p = 0.09)、ある層では自己判定より悪く、コストは 2〜2.5 倍だった。判定者呼び出しに使う予算は、モデル自体か決定論的検査に使う方がよい。

## 8. 関連研究

*(方向性のみ; 引用は bibliography survey で検証済みのものを使う — 下記注参照。)*

- **LLM+形式ソルバ**(Logic-LM、LINC、SatLM、Proof of Thought): LLM が定式化し決定論的ソルバが推論する。これらは記号基盤が信頼できることを仮定する。我々の貢献は、基盤の前提条件がタスク自身によって破られる失敗事例と、それに続くツール契約の再設計である。
- **verify-before-output / 自己修正**(Chain-of-Verification、SelfCheckGPT、self-consistency): 検証を *LLM 自身が*行うため、生成器の失敗モードを継承する。我々のゲートとの違いは、検査が**決定論的かつ記号的**(KB 所属・型・provenance の二値判定)であり、助言ではなく厳格な前提条件にできる点にある。§6 はこの差を直接測定した: LLM loop-judge は、決定論的検査なら機械的に決定できる場面で、誤った完了宣言を統計的に変えられなかった。FormalJudge(Dafny+Z3 によるエージェント監督)が最も近い形式ゲートの親戚であり、KG-Guard(KBQA 回答の接地性検出)は我々の構成的検査に対する検出器側の対応物である。
- **エージェントメモリエンジン**(Zep/Graphiti、A-MEM、WorldDB、ElephantBroker): 知識を永続化するが検証は LLM か埋め込みに委ねる。フロンティア LLM が無効化/更新済みメモリを見逃すという STALE / Supersede の測定は、決定論的監査の動機になる。オントロジー制約付き企業エージェント(arXiv:2604.00555)は出力側の検証を足すが閉包意味論も provenance もない。Salovskii(arXiv:2604.20795)は永続 RDF/OWL+制約検証ループとして最も近いが、閉包前監査の意味論と provenance 同梱判定を欠く。
- **矛盾 KB 上の推論**: paraconsistent / repair ベースの意味論が形式的に研究してきた領域。我々の論点は、標準的な OWL-RL 実体化器を LLM 消費者と本番で合成したときの*システム的*帰結である。[TODO: 投稿前に inconsistency-tolerant semantics の標準的引用を 1–2 件選ぶ。]

## 9. 限界

- **合成監査 KB。** グリッド(≤2000 主張、注入された functional/disjointness 違反)は合成かつ小規模で、全文脈 LLM ベースライン(B1)も P/R 1.0 を達成する。この規模での記号パイプラインの優位はコストと機構であり、見出しの精度ではない。有機的な矛盾を持つ実企業 KB は今後の課題。
- **claim 検証の RQ は判別力を持たなかった。** 対の claim 検証実験は飽和した — 合成 claims では自明でない全条件が全スケールで 1.0 — ため、記号接地がそこで*必要*かは検定できなかった。null design として報告し、証拠には使わない。推論必須 claims への agentic-search ベースラインは計画済み・未実施。
- **単一モデル系列・限られた run 数。** 監査結果は Sonnet 級 1 モデルで 3 runs/セル(安価モデルでの再現を計画中)。QA ゲートの結果は条件毎に単一 run+対応あり McNemar であり、run 間分散ではない。
- **違反クラス。** `kb_violations` は現在 functional property と disjointness をカバーする。閉包前列挙の戦略は他の OWL-RL 表現可能な制約にも拡張できるはずだが、未測定。
- **ベンチマーク形状のゲート。** `kb_check_answer` の起点除外検査は MetaQA の解答規約をゲートにコンパイルしたものである。「設問意味論を記号検査にコンパイルする」一般パターンの実例として提示するが、MetaQA を超えた一般性は未検証。
- **ネガティブコントロールの射程。** 完了宣言の実験は手書きの実行不能仕様 20 問(セル毎に単一 run)で、判定者はエージェントと同じモデル系列である。異系列の判定者や best-of-N 判定なら誤りの相関が切れる可能性があり、未検証。データが支持する控えめな結論 — この標準的な判定者構成は決定論的ゲートの代替にならない — のみを主張する。

## 10. 結論

健全な推論器を、矛盾した KB と従順な LLM と合成した結果は、完全に再現可能な誤答を出す Precision 0.05 の監査だった — そして修正はより良いモデルでもより良いプロンプトでもなく、より良いツール契約だった: 閉包の前に違反を列挙し、全ての判定に provenance を添え、LLM の出力を決定論的検査でゲートする。同じゲート原理をマルチホップ QA に移植すると、負けていた記号層(0.79 < grep のみの 0.86)が決定的に勝つ層(0.97)に変わった。そしてネガティブコントロールが決定論性の必須性を示す: 決定論的検査を LLM 判定者に置き換えても誤った完了宣言は統計的に変わらなかった。同じ系列の判定者は、エージェントが失敗する場面で失敗するからである。産業 NeSy システムへの教訓はアーキテクチャ的である: **記号層が価値を生むのは、LLM が参照してもよい任意の道具としてではなく、LLM の出力が必ず通過する必須の決定論的ゲートとしてである。**
